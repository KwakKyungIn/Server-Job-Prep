2-1. 서버 권위 이동 검증: 필요한 이유

클라이언트 입력은 제안, 위치 확정은 서버 책임

이동은 클라이언트가 전달하는 입력(요청)이며, 최종 위치는 서버가 규칙 검증을 거친 결과로 확정됩니다. 서버 검증을 통과한 좌표만 월드 상태에 반영되고, 그 결과가 다른 클라이언트에 동기화됩니다.

클라이언트 신뢰 시 실제 문제

1) 속도핵 / 텔레포트

비정상 delta를 반영하면 짧은 시간에 과도한 거리 이동이 가능해진다.

2) 벽 통과 / 비정상 지형 진입

충돌 지형을 무시한 좌표가 그대로 적용되면 월드 규칙이 깨진다.

3) 시퀀스 역전 / 재전송 패킷

과거 패킷이 최신 상태를 덮어써 위치 롤백이나 순간이동이 발생한다.

결과: 월드 상태 오염 → 전투 공정성 저하 → 클라이언트 간 위치 불일치(Desync)

서버 권위 설계 원칙

  • 서버가 `seq`, `dt`, `speed`, `navmesh`를 순차 검증
  • 비정상 요청은 drop 또는 clamp/slide 보정
  • 검증 완료 좌표만 월드 상태로 commit
  • 확정 결과만 AOI 대상에게 `S_MOVE` 브로드캐스트

검증 경계(제출 포인트)

  • 입력 안정성: NaN/Inf/Crazy Position 즉시 거부
  • 순서/시간: 역순 seq drop, dt 최소/최대 clamp
  • 속도: 허용 거리 초과 시 이동 거리 제한
  • 지형: NavMesh ValidateMove 통과 좌표만 반영

위협-대응 구조 다이어그램

flowchart LR
  A[Client Sends Position] --> B{Trust Client As-Is?}
  B -->|Yes| C1[Speed Hack / Teleport]
  B -->|Yes| C2[Wall Clip / Invalid Terrain]
  B -->|Yes| C3[Seq Reorder / Replayed Packet]
  C1 --> D[World State Corruption]
  C2 --> D
  C3 --> D
  D --> E[Combat Fairness Break + Desync]
  B -->|No: Server Authoritative| F[Server Validation]
  F --> G[Seq Check + dt Clamp + Speed Check + NavMesh]
  G --> H[Commit + S_MOVE Broadcast]

2-2. AOI 최적화: 먼저 대상을 줄인다

패킷 크기보다 먼저, 보내는 대상 수를 줄여야 한다

문제 정의 엔티티 수가 증가할수록 전체 브로드캐스트는 전송 루프와 송신량이 함께 폭증한다. 여기에 입장/재접속 시 대량 스폰이 겹치면 순간 버스트가 커져 초기 동기화가 불안정해진다.
해결 방향 1단계로 AOI를 적용해 전송 대상을 후보군 수준에서 먼저 줄인다. 2단계로 Snapshot Batching을 적용해 begin/end 경계와 배치 단위 전송으로 초기 동기화 트래픽을 제어한다. 즉, 평시에는 AOI로 불필요 전송을 줄이고, 입장/재동기화 순간에는 스냅샷 경계 처리로 버스트를 완화한다.

브로드캐스트 방식의 한계

  • 엔티티 증가 시 O(N x M) 전송 루프 확대
  • CPU: 직렬화/필터 루프 비용 증가
  • 네트워크: 송신 버퍼 급증, 지연 확대

AOI + Snapshot 적용 전략

  • SpatialGrid로 후보군 1차 축소
  • 거리 + Connectivity로 2차 필터링
  • 입장 동기화는 snapshot_id + begin/end 경계로 명확화
  • 스폰 데이터는 배치 단위로 분할 전송해 버스트 완화

Before vs After

구분 기존 개선
대상 선정 전체 브로드캐스트 AOI 후보군 한정
판정 기준 거리 위주 거리 + 연결성
입장 동기화 대량 스폰 단발성 전송 snapshot begin/end + 배치 전송
결과 불필요 전송 다수 유효 대상 중심 전송

2-2는 AOI(대상 축소)와 Snapshot Batching(버스트 완화)을 함께 적용해 전송 효율과 초기 동기화 안정성을 동시에 높인다.

2-2. Snapshot Batching: 입장 버스트 완화

snapshot_id + begin/end로 경계를 명확히 보낸다

Problem 입장 직후 대량 스폰을 한 번에 전송하면 버스트로 인해 초기 로딩 완료 시점이 불명확해진다. 스냅샷을 경계 기반으로 분할해 전송 순서와 완료 시점을 프로토콜로 명확히 고정해야 한다.

스냅샷 경계 규칙

  • 첫 패킷은 snapshot_begin=true로 시작
  • 마지막 패킷은 snapshot_end=true로 종료
  • 빈 스냅샷도 begin/end를 함께 전송해 로딩 정지 방지

배칭 전송 정책

  • 엔티티를 배치 단위로 분할 송신해 송신 버스트 완화
  • forceFullSnapshot 경로도 동일한 begin/end 규칙 적용
  • 클라이언트는 snapshot_end=true 수신으로 완료 시점 확정

begin/end 시퀀스 타임라인

예시(Players 73 / Monsters 182 / Projectiles 41, 배치 50/100/200) 기준으로 총 5개 패킷 흐름.

  1. 1

    시퀀스 1 · Begin

    S_SPAWN #1

    snapshot_id=K / begin=true / end=false

    첫 배치(Player 1~50) 전송과 함께 경계를 연다. 클라는 K 스냅샷 누적 상태로 진입한다.

  2. 2

    시퀀스 2 · Middle xN

    S_SPAWN #2 ~ #4

    snapshot_id=K / begin=false / end=false

    남은 배치(Player 51~73, Monster 1~100, Monster 101~182)를 순차 전송하며 동일 K에 누적한다.

  3. 3

    시퀀스 3 · End

    S_SPAWN #5

    snapshot_id=K / begin=false / end=true

    마지막 배치(Projectile 1~41)에서 경계를 닫는다. 클라는 K 완료를 수신하면 로딩을 해제한다.

예외 케이스: 스폰 0건이면 S_SPAWN(begin=true,end=true) 1개만 보내 즉시 완료를 보장한다.
