시스템 아키텍처

LoginServer / GameServer / DBAgent / Redis / RDBMS 연동 구조

Architecture Flow

flowchart LR
  C[Client]
  L[LoginServer]
  G[GameServer]
  D[DBAgent]
  R[(Redis)]
  DB[(RDBMS)]

  C -->|login/auth| L
  L -->|token issue| R
  C -->|enter/play| G
  G -->|token verify| R
  G -->|S2S save/load| D
  D -->|ODBC| DB
  G -->|dirty cache| R

인증/입장 경로

  • C_LOGIN → Token 발급/저장 → C_ENTER_GAME 검증 → 월드 입장
  • LoginServer/Redis에서 인증 상태를 확인한 뒤 GameServer 입장 처리

플레이 경로

  • 이동/전투/거래는 GameServer 액터 경로에서 직렬 처리 후 반영
  • 서버 권위 판정 이후 주변 AOI 대상에게 결과 전파

저장 경로

  • Redis Dirty 누적 → S2S_REQ_SAVE_* → DBAgent 트랜잭션 커밋
  • 종료 시 Flush를 수행해 미커밋 데이터 누락 최소화

핵심 포인트

인증/토큰은 LoginServer + Redis에서 처리하고, 게임플레이 권위 로직은 GameServer에 집중한다. DB I/O는 DBAgent로 분리해 트랜잭션을 전담하며, 캐시(Redis)와 영속화(RDBMS)를 역할 분리했다.

컴포넌트 책임

LoginServer는 로그인/토큰 발급(TTL 300초), GameServer는 룸/전투/이동/거래 서버 권위 판정, DBAgent는 ODBC 트랜잭션(BEGIN/COMMIT) 전담으로 구분한다.

End-to-End 데이터 흐름

Login → Enter → Play → Save → Exit

Sequence Flow

sequenceDiagram
  participant C as Client
  participant L as LoginServer
  participant R as Redis
  participant G as GameServer
  participant D as DBAgent
  participant DB as RDBMS

  C->>L: C_LOGIN
  L->>R: save token(TTL)
  L-->>C: S_LOGIN(token)

  C->>G: C_ENTER_GAME(token)
  G->>R: token verify
  G-->>C: enter world

  C->>G: move / combat / trade
  G->>R: dirty write-back

  G->>D: S2S_REQ_SAVE_*
  D->>DB: BEGIN...COMMIT
  D-->>G: save result

  C-->>G: disconnect
  G->>D: flush pending save

구간별 의도

  • Login: 인증 + 토큰 발급
  • Enter: 토큰 검증 + 로딩 게이트
  • Play: 서버 권위 판정 + 캐시 반영
  • Save: Dirty 수집 후 트랜잭션 저장
  • Exit: 종료 시점 Flush로 누락 방지

주요 저장 이벤트

  • S2S_REQ_SAVE_PLAYER_CORE
  • S2S_REQ_SAVE_INVENTORY
  • S2S_REQ_SAVE_QUICKSLOT
  • S2S_REQ_TRADE_COMMIT / S2S_RES_TRADE_COMMIT

실패 시 처리 원칙

  • DB 실패 시 ROLLBACK으로 원자성 유지
  • 종료 시 Flush로 미커밋 데이터 손실 최소화
  • 로딩 게이트 실패 시 입장 차단 + 세션 정리
