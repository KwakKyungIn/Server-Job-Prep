# Velog 시리즈 기획서 v1.2 — MMO 서버 포트폴리오 기록 계획 (복붙용)

> 목표: **신입 서버 개발자** 관점에서, 프로젝트의 핵심 기술/기능을 **읽히는 순서**로 정리한다.  
> 키워드: **기본기(네트워크/동시성)** + **실무 감각(권위/동기화/정합성)** + **성장(실패->개선)**

---

## 1) 포지셔닝(신입 최적화)

### 1.1 독자
- 게임 서버 면접관 / 실무 서버 개발자
- 서버 공부하는 취준생(학습 로드맵으로도 읽힘)

### 1.2 "이 시리즈가 보여줘야 하는 것"
- **기본기**
  - IOCP 기반 네트워크 구조(Overlapped/Completion/Dispatch)
  - 패킷 파이프라인(헤더/ID/핸들러 디스패치/역직렬화)
  - 스레딩 모델(네트워크-로직 분리, 큐 기반 처리)
- **실무 감각**
  - 서버 권위(치팅 입력 검증/보정)
  - AOI 최적화(대규모 동기화 비용 줄이기)
  - 데이터 정합성(거래 원자 커밋/트랜잭션/캐시 Write-Back)
- **성장 가능성**
  - "처음엔 이렇게 했다가 터졌고 -> 측정했고 -> 이렇게 고쳤다"를 매 편에 1개 이상 포함

---

## 2) 전체 구성: 3막 구조(상향식)

> 흐름: **기초(연결/패킷/동시성) -> 월드 운영(권위/AOI/Tick) -> 운영 안정성(정합성/경제/파티)**  
> 학습 순서와 글 순서를 일치시키는 게 면접에서 가장 세다.

### Act 0 — 프롤로그(시리즈 0편)
- 0편: 왜 MMO 서버를 만들었나 + 프로젝트 한 장 요약
  - 문제의식: MMO 서버가 어려운 이유(동시성/치팅/대규모 동기화)
  - 목표: "완성도"보다 "핵심 기술을 끝까지 구현"에 집중
  - 아키텍처 다이어그램(멀티 서버 구성 + 대표 요청 흐름 3개)
  - 이 시리즈를 읽으면 얻는 것(기술 키워드/순서 안내)

---

## 3) 시리즈 목차(복붙용)

### Act 1 — 서버의 뼈대(네트워크/동시성/성능)
1편: IOCP 네트워크 레이어 — Overlapped 기반 Session/Dispatch 구조  
2편: 패킷 파이프라인 — 헤더/ID/핸들러 매핑, 역직렬화, 디스패치  
3편: Hybrid 스레드 모델 — 네트워크 스레드 vs 로직 워커 분리 이유  
4편: JobQueue/GlobalQueue — 경합 줄이는 큐 기반 처리, 직렬화 설계  
5편: 송신/메모리 최적화 — 풀링, SendBuffer 전략, 백프레셔(폭주 방지)  
6편: 개발 생산성 도구 — 패킷 코드 생성기/자동화(반복 작업 제거)

### Act 2 — 실시간 월드 운영(동기화/치팅/게임플레이)
7편: RoomActor & 룸 라이프사이클 — 룸 단일 실행 경로, 입장/퇴장/정리  
8편: 서버 권위 이동 검증 — 치팅 입력 방어(검증/보정/예외 처리)  
9편: NavMesh 슬라이딩 보정 — 이동 보정의 현실적인 타협(벽/모서리 처리)  
10편: AOI/SpatialGrid — 후보 수집/필터/Spawn-Despawn, 비용 구조  
11편: 스냅샷 배칭 — 대규모 동기화 패킷 폭주 줄이기(전송 전략)  
12편: 투사체 시스템 — 서버 tick 갱신/충돌/벽 레이캐스트, 동기화  
13편(선택): 몬스터 FSM + 네비/LOS — 서버 주도 AI와 부하 최적화 포인트  
14편(선택): 인스턴스/채널 운영 — 맵 이동 핸드셰이크, 인스턴스 자동 정리

### Act 3 — 운영 안정성 & 경제 시스템(정합성/거래/파티)
15편: Redis Write-Back + AutoCommit — Dirty 누적/주기 저장/로그아웃 플러시  
16편: ODBC 트랜잭션 & 커넥션 풀 — Prepared/Transaction으로 원자성 확보  
17편: 거래 상태머신 — Ready/Confirm/Cancel, 타임아웃/중복 요청 방어  
18편: 거래 원자 커밋 — 아이템 복사/증발 방지(Phase1 + DB Commit 설계)  
19편: 파티(크로스 룸) — 초대/탈퇴/파티 채팅/상태 스냅샷 팬아웃  
20편: 운영 관점 회고 — 병목/미완성/개선 방향(측정 기반으로)

## 4) 각 편 "목표/산출물" 규격(통일)

> 모든 글은 아래 산출물을 최소로 포함한다. 이게 "포폴 느낌"을 만든다.

### 4.1 각 편 필수 산출물 체크리스트
- [ ] 요약 3줄(무엇/어떻게/결과)
- [ ] 텍스트 다이어그램 1개(없으면 ASCII로)
- [ ] 핵심 코드 스니펫 3~5개(함수 3개 이하 중심)
- [ ] 실패/삽질 1개(재현/원인/수정)
- [ ] 경계조건 3개 이상(중복/역순/타임아웃/끊김/재접속/악성 입력)
- [ ] 트레이드오프 2개 이상(얻은 것/잃은 것)
- [ ] 테스트/측정(가능하면 수치, 아니면 로그/체크 포인트)
- [ ] 다음 편 예고 2줄(+ 링크 자리)

### 4.2 증거(코드 근거) 표기 규칙
- "근거 파일 스니펫 + 핵심 함수 이름"을 항상 남긴다

- 어떻게 해결: (한 줄)
- 결과/효과: (한 줄, 가능하면 수치/로그)

## 1. 필요했던 이유
- 증상: (예: CPU 폭주 / 패킷 폭주 / 치팅 입력 / 데이터 불일치)
- 요구사항: 정확성 / 성능 / 운영 안정성 중 무엇이 핵심인지 명시
- 내 제약: (시간/구현 난이도/구조적 제약)

## 2. 첫 시도와 실패(삽질)
- 첫 구현: (왜 그렇게 생각했는지)

- 교훈: (한 줄)

## 3. 어떻게 풀었나
- 설계 목표: (정확성/성능/단순성 우선순위)
- 핵심 아이디어: (텍스트 다이어그램 or 간단한 흐름도)
- 스레딩/큐/상태 전이: (어떤 단위로 직렬화했는지)

## 4. 구현의 핵심(코드 스니펫 3~5개)
- 근거 파일/함수:
  - (경로) :: (함수명)
- 스니펫 #1: (핵심 로직)
- 스니펫 #2: (핵심 로직)

## 5. 경계조건/실패 케이스

- 케이스 2: (타임아웃 / 끊김 / 재접속)
- 케이스 3: (악성 입력 / 치팅 / 비정상 값)

- 재현 시나리오:

  - 예: Tick 평균/최대, 패킷 수, DB commit 횟수, 캐시 hit 등

## 6) 각 Act별 "한 줄 전략" (글을 잃지 않게 잡아주는 가드레일)

### Act 1 전략
- "네트워크/동시성 기본기 증명"이 전부다.
- 코드가 많아 보이면 안 된다. **핵심 흐름**만 보여준다.

### Act 2 전략
- "서버 권위 + 대규모 동기화"로 실무 감각을 찍는다.
- AOI/권위 검증은 면접 질문이 바로 나오니 **경계조건**을 특히 많이 쓴다.

### Act 3 전략
- "아이템 복사/증발 방지" 같은 운영 이슈를 **구체 사례**로 잡는다.
- 거래/Write-Back은 설계 그림 + 상태/트랜잭션 경계를 명확히 보여준다.

## 7) 제목 규칙(면접관이 반응하는 형태)

- 추상어 금지, "게임 서버 문제"로 제목을 만든다.
  - 나쁨: 데이터 정합성
  - 좋음: 아이템 복사/증발을 막는 거래 원자 커밋
  - 나쁨: 동시성
  - 좋음: RoomActor 직렬화로 락 제거한 이유
  - 나쁨: 최적화
  - 좋음: AOI 스냅샷 배칭으로 패킷 폭주 줄이기
- 제목에 "무엇을 막았는지/줄였는지/보장했는지"를 넣는다.

## 8) 운영 계획(발행/퀄리티 관리)

### 8.1 발행 리듬(권장)
- 주 2편 기준(짧게 꾸준히)
- 길이 가이드:
  - 일반 편: 1200~1800자(핵심만)
  - 묵직한 편(AOI/거래/Write-Back): 2500~3500자(그림 + 케이스 포함)

### 8.2 발행 전 QA 체크
- [ ] 요약 3줄만 읽어도 "가치/결과"가 보이는가
- [ ] 실패/삽질이 "진짜로" 하나 들어갔는가
- [ ] 경계조건이 최소 3개 이상인가
- [ ] 트레이드오프가 솔직한가(장점만 있으면 얕아 보임)
- [ ] 다음 편 예고/링크 자리가 있는가

## 9) 다이어그램 템플릿(복붙용)

### 9.1 패킷 흐름(예시)

```text
[Client]
  └─ C_MOVE ───────> [GameServer / IOCP Thread]
                      └─ Parse Header & Dispatch
                          └─ Enqueue Job (RoomActor)
                              └─ Validate & Correct
                                  └─ Broadcast S_MOVE
  <──── S_MOVE ───── [Other Clients]
```

### 9.2 거래 상태머신(예시)

```text
Idle
 └─ RequestTrade -> Proposed
        ├─ BothReady -> Locked
        │      ├─ Confirm -> Commit(DB Tx)
        │      └─ Timeout/Cancel -> Rollback -> Idle
        └─ Reject -> Idle
```

## 11) Act 글 스타일 보정 가이드(추가)

### 11.1 글 흐름 고정
- `요약 3줄 -> 필요했던 이유 -> 첫 시도와 실패 -> 어떻게 풀었나 -> 구현의 핵심 -> 경계 조건 -> 트레이드오프 -> 테스트/측정 -> 회고/다음 편` 순서를 유지한다.

### 11.2 문장 톤
- 과장 대신 관찰 기반 표현을 쓴다.
  - 예: "극적으로 빨라졌다" 대신 "Accept 지연 로그가 줄었다"
- 추상어 대신 상황 중심으로 쓴다.
  - 예: "정합성을 강화했다" 대신 "거래 확정 시 두 플레이어 인벤토리를 하나의 커밋 경계로 묶었다"
- 섹션 첫 문장을 결론형 한 줄로 시작한다.
  - 예: "핵심은 완료 통지의 관문을 하나로 고정한 것이다."

### 11.3 소제목
- `##` 번호 제목 유지 (`1.`, `2.`, `3.` ...)
- `###` 보조 섹션은 1개만 두고, 보통 `3.1 흐름 요약 다이어그램`으로 고정한다.
- 제목은 기술명보다 해결한 문제를 앞세운다.
