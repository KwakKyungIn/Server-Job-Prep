# 🌐 Sun의 네트워크 파일 시스템 (NFS) — OSTEP Chapter 51

> 이 장에서는 Sun Microsystems의 NFS(Network File System)를 통해  
> **분산 파일 시스템**이 어떻게 설계되고 동작하는지를 살펴본다.  
> 특히 NFS의 무상태(stateless) 설계와 캐시 일관성 문제 해결 방법이 주요 주제다.

---

## ❓ 핵심 질문

> **분산 환경에서도 파일 시스템을 안전하고 효율적으로 제공할 수 있을까?**  
> 서버가 충돌하거나 네트워크가 불안정하더라도 사용자는 로컬 디스크처럼 접근 가능해야 한다.  
> 이를 위해 Sun의 NFS는 어떤 방식으로 설계되었을까?

---

## 🔍 상세 개념 정리

---

### 51.1 기본적인 분산 파일 시스템

- **분산 파일 시스템 (Distributed File System)**:  
  여러 대의 컴퓨터가 동일한 파일 시스템을 **네트워크를 통해 공유**.

- **구조**:
  - **서버**는 저장소(디스크)를 가지고 있고,
  - **클라이언트**는 그 저장소를 로컬처럼 사용.

- **사용 예**:
  - 클라이언트가 `/remote`에 서버의 디렉토리를 mount.
  - 이후 `cd /remote` → `ls`, `cat` 등 모든 작업이 로컬처럼 동작.

- **목표**:
  - **투명성**: 사용자는 네트워크 파일 시스템인지 모름.
  - **호환성**: POSIX 파일 인터페이스를 그대로 제공.

---

### 51.2 NFS에 대하여

- **NFS (Network File System)**:
  - Sun Microsystems에서 1980년대 초 개발.
  - 분산 환경에서 공유 디스크 없는 워크스테이션을 만들기 위해 고안.

- **오픈 프로토콜 (Open Protocol)**:
  - 누구나 구현할 수 있도록 명세를 공개.
  - 다양한 운영체제에서 폭넓게 채택됨 (리눅스, BSD, Solaris 등).

- **기술적 기반**:
  - **Sun RPC (Remote Procedure Call)**:  
    클라이언트의 로컬 함수 호출처럼, 서버 측 함수를 호출할 수 있게 함.

- **구성 요소 요약**:

| 구성 요소 | 설명 |
|-----------|------|
| 클라이언트 | 원격 서버의 파일 시스템을 마운트하여 사용 |
| 서버 | 디스크 저장소를 소유하고 요청을 처리 |
| RPC | 클라이언트와 서버 간의 통신을 추상화 |

---

### 51.3 핵심: 단순하고 빠른 서버 크래시 복구

- **서버는 크래시 날 수 있다** → 서버 복구 시 클라이언트는 무사히 작동해야 함.

- Sun의 디자인 목표:
  1. 서버가 재시작되더라도 별도의 복구 프로토콜 없이 클라이언트가 정상 작동할 것
  2. 파일 시스템이 자동으로 **정합성 유지**할 것
  3. 시스템이 **상태 정보 없이 작동**할 수 있을 것

- 이를 위해 NFS는 **상태 비저장(stateless)** 서버 설계를 채택함.

---

### 51.4 빠른 크래시 복구의 열쇠: 상태를 유지하지 않음

- **Stateless Server**:
  - 서버는 클라이언트의 상태를 전혀 기억하지 않음.

- 예시:  
  클라이언트가 파일을 열면 서버는 해당 세션, 오프셋, 권한 등 **어떤 정보도 저장하지 않음**.  
  대신 클라이언트가 매 요청마다 **필요한 모든 정보**를 제공함.

- **장점**:
  - 서버 크래시 후 빠르게 복구 가능 (상태 복원 필요 없음)
  - 병렬성과 확장성 향상
  - 단순하고 안전한 설계

- **단점**:
  - 클라이언트는 매 요청마다 많은 정보를 보내야 함 (→ 오버헤드 증가)
  - 캐시 일관성 유지가 어렵고 불완전함

### 51.5 NFSv2 프로토콜

- NFSv2는 **파일 이름 기반**이 아닌, **파일 핸들(file handle)** 기반으로 작동함.

#### 🔹 파일 핸들 (File Handle)
- 클라이언트가 서버에 `LOOKUP` 요청을 보내면, 서버는 해당 파일의 핸들을 반환.
- 이후의 모든 연산(`READ`, `WRITE`, `GETATTR` 등)은 이 핸들을 기반으로 수행됨.
- 핸들은 일반적으로 다음 정보를 포함:
  - 파일 시스템 ID
  - 아이노드 번호
  - 파일 생성 번호 등

> 즉, 클라이언트는 `"/foo/bar"`처럼 경로를 반복적으로 보내지 않고, 한번 받은 핸들을 계속 사용.

#### 🔹 주요 RPC 호출

| 호출 | 설명 |
|------|------|
| `LOOKUP(dir_handle, name)` | 디렉터리 내에서 파일 이름 검색 후 핸들 반환 |
| `READ(file_handle, offset, count)` | 파일 내용을 읽음 |
| `WRITE(file_handle, offset, data)` | 파일에 데이터를 씀 |
| `GETATTR(file_handle)` | 파일의 메타데이터(크기, mtime 등) 조회 |
| `SETATTR(file_handle, attrs)` | 파일 속성 설정 |

> 프로토콜은 **RPC 기반**으로 동작하며, 클라이언트의 로컬 함수 호출처럼 보이지만 내부적으로는 네트워크 요청이다.

---

### 51.6 프로토콜에서 분산 파일 시스템으로

이 절에서는 프로토콜이 실제 분산 시스템에서 어떻게 작동하는지를 설명한다.

#### 🔸 예: `open("/mnt/foo/bar.txt")`

1. 클라이언트는 `/mnt/foo` 디렉터리 핸들을 서버에서 받는다.
2. 그 핸들과 `bar.txt` 이름을 이용해 `LOOKUP()` 요청을 보냄.
3. 서버는 `bar.txt`의 파일 핸들을 반환.
4. 클라이언트는 이 핸들을 저장하고 `READ`, `WRITE` 등에 사용.

> 분산 시스템에서도 클라이언트는 **파일 핸들만 있으면 경로를 다시 지정할 필요 없이 파일에 접근 가능**.

---

### 51.7 서버의 고장을 멱등 연산으로 처리하기

- **멱등성 (Idempotency)**:
  - 같은 연산을 여러 번 실행해도 **결과가 동일**해야 함.

#### 🔹 왜 필요한가?

- 서버가 다운되거나 응답이 없을 때, 클라이언트는 **RPC 요청을 재전송**할 수 있음.
- 재전송이 문제가 되지 않으려면 연산은 멱등해야 함.

#### 🔹 멱등한 연산 예

| 연산 | 설명 |
|------|------|
| `READ`, `GETATTR` | 단순히 정보를 읽는 작업 → 결과가 항상 동일 |
| `WRITE` (NFSv2) | 지정된 오프셋에 데이터를 덮어씀 → 결과 보장됨

> `CREATE`, `REMOVE` 등은 멱등하게 만들기 어려움 → 서버는 이런 연산에서 특별한 주의가 필요하다.

---

### 51.8 성능 개선하기: 클라이언트 측 캐싱

NFS는 성능 향상을 위해 **클라이언트에 캐시 기능**을 제공함.

#### 🔹 캐시 대상

- **파일 데이터**: 자주 읽는 데이터 블록
- **디렉터리 목록**: `ls` 명령어 성능 향상
- **파일 속성**: 파일 크기, 수정 시간 등 메타데이터

#### 🔹 캐시 정책

| 항목 | 설명 |
|------|------|
| **read-ahead** | 파일을 순차적으로 읽는 경우, 다음 블록을 미리 로딩 |
| **delayed write** | `write()` 호출 후 즉시 서버에 보내지 않고 로컬에 저장 |
| **close() 시 flush** | 파일 닫을 때 변경 내용 서버로 전송

> 캐시는 성능을 극대화하지만, 일관성(consistency) 문제를 야기할 수 있음.

---

### 51.9 캐시 일관성 문제

- 여러 클라이언트가 동일 파일을 수정하거나 읽는 경우, **캐시된 데이터가 실제 상태와 불일치**할 수 있음.

#### 🔹 예시

1. 클라이언트 A가 `foo.txt`를 수정하고 저장
2. 클라이언트 B는 여전히 이전 데이터를 캐시하고 있음
3. 결과적으로 B는 오래된 데이터를 읽게 됨

#### 🔹 해결 방법 (기초)

- **주기적 유효성 검사**:
  - 클라이언트는 일정 시간마다 서버에 `GETATTR()`을 호출하여 `mtime` 확인
  - 변경되었으면 캐시 무효화

- **TTL 기반 캐시**:
  - 캐시 유효 시간을 설정하고, 만료 시 재검사

- **파일 닫을 때 동기화**:
  - `close()` 호출 시 서버로 변경 내용을 전송

> 하지만 이런 방법들은 **완전한 일관성을 보장하지 않음** → 일부 애플리케이션에는 위험

---

### 51.10 NFS의 캐시 일관성 기법에 대한 평가

NFS는 일관성 유지 전략으로 **"좋은 시도(best-effort)"** 수준만 제공함.

#### 🔹 캐시 일관성 요약

| 전략 | 설명 |
|------|------|
| `GETATTR()` 주기적 호출 | 서버에서 mtime을 확인하여 변경 여부 판단 |
| TTL 기반 무효화 | 캐시된 블록이 일정 시간 지나면 무효화 |
| `close()` 시 flush | write-behind 캐시를 서버로 반영 |

#### 🔹 문제점

- **정밀 제어 불가**: 정확한 시점에서 다른 클라이언트의 변경을 알 수 없음
- **간섭 없음 보장 불가**: 클라이언트 간의 업데이트 충돌 가능
- **모순된 캐시 허용**: 실제 서버 상태와 불일치한 데이터를 읽을 수 있음

> 따라서 NFS는 **"좋은 일관성"은 제공하지만, 완전한 일관성은 아님**.  
> 분산 데이터베이스처럼 강한 일관성을 요구하는 시스템에는 부적합.

---

### 51.11 서버 측 쓰기 버퍼링의 의미

NFS는 **서버도 쓰기를 즉시 디스크에 기록하지 않을 수 있음**.

#### 🔹 이유

- 디스크 I/O는 느림 → 성능 향상을 위해 **버퍼링(write buffer)** 사용

#### 🔹 문제점

- **서버 크래시 시 데이터 손실 가능성**  
  → 클라이언트는 쓰기가 완료되었다고 생각하지만, 실제로는 디스크에 기록되지 않았을 수 있음

#### 🔹 해결 전략

- 일부 구현에서는 `fsync()` 호출을 통해 강제 디스크 기록 가능
- 클라이언트가 확실한 저장을 원한다면 `O_SYNC` 옵션 사용 가능

> 다시 말해, **NFS의 쓰기 완료는 반드시 디스크 반영을 보장하지는 않는다.**

### 51.12 요약

| 항목 | 설명 |
|------|------|
| 설계 철학 | 무상태(stateless) → 서버 복구 용이, 간결한 구조 |
| 파일 핸들 | 경로 기반 접근 대신, 핸들 기반 접근으로 효율성 향상 |
| 일관성 | 클라이언트 캐시 사용 가능하나 완벽한 일관성은 아님 |
| 성능 최적화 | read-ahead, write-behind, TTL 캐시 등 |
| 한계점 | 강력한 일관성 요구 시스템에는 부적합 |
| 멱등 연산 | 중복된 요청에도 안전한 설계로 신뢰성 향상 |
| 보안 | 기본 RPC 기반이므로 보안 취약 (추후 인증 기능 필요)
