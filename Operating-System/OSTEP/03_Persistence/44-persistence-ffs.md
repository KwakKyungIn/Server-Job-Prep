# 🚀 지역성과 Fast File System (FFS) — OSTEP Chapter 44

> 이 장에서는 전통적인 Unix 파일 시스템의 성능 한계를 분석하고, 이를 극복하기 위한 Berkeley Fast File System(FFS)의 설계 전략을 다룬다.  
> FFS는 디스크의 물리적 특성을 고려한 배치 정책, 실린더 그룹 개념, 지역성 향상 기법 등을 통해 성능을 대폭 향상시킨 대표적인 파일 시스템이다.

---

## ❓ 핵심 질문

> 디스크가 느리다는 사실을 인지한 뒤, 어떻게 하면 **디스크의 물리적 특성을 반영하여**  
> 더 빠르고 효율적인 파일 시스템을 구현할 수 있을까?

---

## 🔍 상세 개념 정리

---

### 44.1 문제: 낮은 성능

#### 📌 문제 배경

- 초창기 Unix 파일 시스템은 단순한 구조였지만, **디스크 접근 비용**을 고려하지 않았다.
- 파일의 inode와 데이터 블록이 물리적으로 멀리 떨어져 있어, 매 접근마다 디스크 헤드 이동이 발생.

#### 📉 성능 문제 요약

| 원인 | 결과 |
|------|------|
| 비효율적인 블록 배치 | 디스크 헤드가 자주 이동함 |
| 빈 블록 리스트 기반 할당 | 블록들이 흩어져 단편화 발생 |
| 작은 블록 크기 (512B) | 출력 단위가 작아 비효율 발생 |

> 📌 대표적 문제: `아이노드`는 한 곳에, `데이터 블록`은 다른 곳에 → 디스크 탐색 과도

---

### 44.2 FFS: 디스크에 대한 이해가 해답이다

Berkeley의 McKusick 팀은 **디스크 친화적**인 구조를 목표로 Fast File System(FFS)을 개발했다.

#### 🎯 핵심 전략

- **파일 시스템 인터페이스 유지** (`open`, `read`, `write`, `close`)  
- 내부 구조만 재설계하여 성능 최적화  
- 기존 응용 프로그램과의 **호환성 유지**

---

### 44.3 파일 시스템 구조: 실린더 그룹

#### 🧱 실린더 그룹(Cylinder Group)

디스크를 여러 구획으로 나누고, 각각을 **작은 독립 파일 시스템처럼** 관리.

| 구성 요소 | 설명 |
|-----------|------|
| 슈퍼블록 복제 | 그룹마다 백업 존재 (신뢰성 향상) |
| 아이노드 비트맵 / 데이터 비트맵 | 해당 그룹의 블록 할당 상태 추적 |
| 데이터 블록들 | 실질적인 사용자 데이터 저장 |

> 🧠 장점: 파일/디렉터리들이 한 그룹 안에 존재하면, 디스크 탐색을 줄일 수 있음

---

### 44.4 파일과 디렉터리 할당 정책

#### 📌 기본 원칙: **관련된 데이터는 가까이 배치하라**

- 디렉터리는 **균형 있게 분산** (그룹 내 프리 아이노드 수 고려)
- 같은 디렉터리 내 파일들은 **같은 그룹에** 저장
- 관련 없는 파일은 **다른 그룹에** 저장

#### 예시

- `/dir1/1.txt`, `/dir1/2.txt` → 같은 그룹
- `/dir99/4.txt` → 다른 그룹

> ❗ 이 전략은 **상식(common sense)** 기반이며, 경험적 근거는 뒤에 나옴

---

### 44.5 파일 접근의 지역성 측정

#### 📊 실험: SEER 트레이스 분석

- 경로 간 거리 0~1 (같은 디렉터리 or 같은 파일) → 전체의 40%
- 거리 2 (상위 디렉터리 공유) → 약 25%

> 🔍 결론: **이름 공간(locality in namespace)** 은 실제 존재하며, FFS의 배치 정책은 유효하다.

---

### 44.6 대용량 파일 예외 상황

#### 문제

- 큰 파일이 **하나의 그룹을 다 차지** → 다른 관련 파일들이 외부로 밀려남 → 지역성 깨짐

#### FFS 전략

- 처음 **12개 블록**은 아이노드와 같은 그룹에
- 그 이후 **간접 블록 단위로 다른 그룹**에 배치

#### 💡 예시 계산

- 디스크 전송 속도: 40MB/s, 탐색 시간: 10ms
- 대역폭의 50% 사용 → 한 번에 409.6KB 청크 전송 필요

> 이 계산은 **점진적 경감(amortization)** 기법의 실제 적용 사례다.

---

### 44.7 FFS에 대한 기타 사항

#### ⚙️ 작은 파일 최적화

- 기본 블록 크기: 4KB → 낭비 발생
- **서브블록(512B)** 단위 할당으로 해결
- 라이브러리 수준에서 4KB 청크로 버퍼링하여 서브블록 사용 최소화

#### 🧠 디스크 배치 최적화

- 순차 읽기에서 회전 지연 방지 위해 **간격 배치**
- 디스크 특성 감지 후 **매개화(parameterization)** 하여 최적 블록 간격 계산

#### 🧰 유용한 기능 추가

| 기능 | 설명 |
|------|------|
| 긴 파일 이름 | 8자 제한 폐지 |
| 심볼릭 링크 | 경로 기반 링크, 하드 링크의 한계 극복 |
| `rename()` | 원자적 이름 변경 지원 |

> 🌟 **기술적 혁신 + 사용성 향상**의 조화 → FFS의 성공 요인
