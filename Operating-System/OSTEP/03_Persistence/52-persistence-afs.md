
# 📡 Andrew 파일 시스템 (AFS) — OSTEP Chapter 52

이 장에서는 Carnegie Mellon University에서 개발한 **Andrew 파일 시스템(AFS)** 에 대해 다룬다.
AFS는 **확장성**을 목표로 설계된 분산 파일 시스템이며, **전체 파일 캐싱(whole-file caching)**, **콜백 기반 캐시 일관성(callback-based consistency)** 등을 통해 NFS와는 다른 접근 방식을 취한다.

---

## ❓ 핵심 질문

> 분산 환경에서 수많은 클라이언트를 효율적으로 지원하려면, 파일 시스템은 어떤 방식으로 캐싱과 일관성을 제공해야 할까?
>
> 어떻게 하면 버(서버)의 부하를 줄이면서도 클라이언트가 항상 최신 상태의 파일을 사용하는 것처럼 느끼게 만들 수 있을까?

---

## 🔍 상세 개념 정리

### 52.1 AFS 버전 1

- **AFS v1의 기본 원칙**: 파일을 열면 서버로부터 전체 파일을 가져와 로컬 디스크에 저장. 이후 read/write는 모두 로컬에서 수행.
- **전체 파일 캐싱 방식**: open() 시 `Fetch` 요청 → 파일 전체를 받아 로컬 디스크에 저장 → close() 시 `Store` 요청으로 변경사항 전송.
- **프로토콜 메시지**:
  - `Fetch`: 전체 파일 가져오기
  - `Store`: 변경된 파일 저장
  - `TestAuth`: 캐시 유효성 확인
  - `GetFileStat`/`SetFileStat`: 파일 상태 정보
  - `ListDir`: 디렉토리 내용 요청

> ✅ 장점: 네트워크 통신 횟수 감소, 로컬 I/O로 빠름
> ❌ 단점: 서버의 디렉토리 순회 비용 높음, `TestAuth` 요청 과다

---

### 52.2 버전 1의 문제점

1. **경로 순회 비용**: 서버는 루트부터 파일까지 경로를 따라가며 탐색 → CPU 소모 큼
2. **TestAuth 트래픽 과다**: 클라이언트는 로컬 캐시 유효성을 확인하기 위해 자주 요청 → 서버 부하 증가
3. **프로세스 기반 구조**: 클라이언트마다 별도 프로세스를 서버에 할당 → 문맥 전환 비용 큼

→ 결과적으로 **20명 이상 클라이언트 지원이 어려움**

---

### 52.3 프로토콜의 개선

- 목표: **서버와의 상호작용 수를 줄이는 것**
- **문제 인식**:
  - 너무 잦은 `TestAuth` → 캐시 검증 방식 개선 필요
  - 경로 순회 대신 **식별자 기반 접근** 필요

---

### 52.4 AFS 버전 2

- 도입한 개념: **콜백(callback)**
  - 서버는 클라이언트에게 "이 파일이 변경되면 알려줄게"라고 약속
  - 클라이언트는 서버로부터 콜백을 받을 때까지 로컬 캐시를 신뢰함

- **경로 탐색 최적화**: 전체 경로 대신 FID(File Identifier) 기반 탐색 수행
- **작동 흐름**:
  1. 클라이언트가 `/home/remzi/notes.txt`를 열면,
  2. 디렉토리 단위로 Fetch 요청 (home → remzi → notes.txt)
  3. 각 단계에서 콜백 설정
  4. 이후 read/write는 로컬 캐시만 사용

> 📌 콜백 기반 모델은 NFS의 polling과 달리 event-driven 방식 → 서버 부하 감소

---

### 52.5 캐시 일관성

- AFS는 변경 사항을 **파일 닫기(close)** 시 서버에 전송
- 서버는 해당 파일을 캐시 중인 모든 클라이언트의 콜백을 끊음 (무효화)
- 클라이언트는 콜백이 끊기면 파일을 다시 요청함 → **최신 상태 보장**

- **동일 기기 내 일관성**: 바로 공유됨 (로컬 메모리 기반)
- **다른 기기 간 일관성**: 콜백을 통해 동기화

> ✅ 일관성 모델이 직관적이며 설명 쉬움

---

### 52.6 크래시 복구

- **클라이언트 크래시**: 재부팅 후 캐시 유효성 검사 (TestAuth)
- **서버 크래시**: 콜백 정보가 메모리에 존재 → 복구 후 클라이언트가 캐시 유효성 재검사

> 🛠 해결책: 재부팅 후 "버가 죽었음"을 인지하도록 heartbeat 메시지 또는 캐시 무효화 전송

---

### 52.7 AFSv2의 확장성과 성능

- **버당 클라이언트 수 증가**: 20명 → 50명 이상
- **성능 향상**: 대부분의 읽기/쓰기 연산이 로컬 디스크 또는 메모리에서 처리
- **워크로드에 따른 비교 (AFS vs NFS)**:
  - 대용량 순차 읽기: AFS가 빠름 (디스크 캐시)
  - 작은 범위 쓰기: NFS가 유리 (블럭 기반 I/O)

---

### 52.8 AFS: 그 외의 개선점들

- **전역 이름 공간(Global Namespace)** 제공 → 클라이언트 간 이름 충돌 없음
- **보안 기능 강화**: 인증 및 접근 제어 리스트 지원
- **관리 도구 제공**: 서버 관리 효율성 향상

---

### 52.9 요약

| 항목 | 내용 |
|------|------|
| 캐싱 방식 | 전체 파일 캐싱 (로컬 디스크) |
| 일관성 | 콜백 기반 무효화 모델 |
| 성능 | 반복 접근 시 빠름 (로컬 캐시 활용) |
| 확장성 | 서버 부하 적고 클라이언트 수 증가 가능 |
| 단점 | 작은 I/O, 부분 갱신에 비효율적 |

AFS는 결국 시장에서 NFS, CIFS 등에 밀려났지만, **콜백 기반 일관성 모델과 전역 이름 공간** 등은 후속 시스템에도 영향을 미쳤다.
