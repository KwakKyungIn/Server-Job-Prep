# 🛡️ 데이터 무결성과 보호 (OSTEP Chapter 47)

파일 시스템은 단순히 데이터를 저장하는 것뿐만 아니라, **저장된 데이터가 손상되지 않고 정확히 유지되는 것**을 보장해야 한다.  
이 장에서는 다양한 **디스크 오류**, **무결성 검증 기법(체크섬)**, **기록 손실 탐지 및 대응 방식**, 그리고 **Scrubbing** 기법까지 포함하여 신뢰성 있는 저장 시스템 구축을 위한 기술을 설명한다.

---

## ❓ 핵심 질문

> 저장 장치에 기록된 데이터가 오랜 시간이 지나도 손상되지 않았다는 걸 어떻게 증명할 수 있을까?  
> 블록 손상, 잘못된 쓰기, 기록 손실 같은 오류는 어떻게 탐지하고 복구할 수 있을까?

---

## 🔍 상세 개념 정리

### 47.1 디스크 오류 모델

- **과거 RAID 시스템**은 디스크 전체가 고장나는 **fail-stop 모델**을 기반으로 설계됨.
- 그러나 **현대 디스크**는 더 복잡한 오류를 겪음. 대표적인 부분 오류 모델:
  - **LSE (Latent Sector Error)**: 손상된 섹터. 읽기 시 에러 반환.
  - **블럭 손상**: 정상처럼 보이나 실제 내용은 잘못됨. "조용한 오류" (silent fault).

#### ❗ 조용한 오류의 위험성

| 종류 | 설명 | 예시 |
|------|------|------|
| LSE | 섹터가 물리적으로 손상됨 | 헤드 크래시, 방사선 |
| 블럭 손상 | 내용이 잘못 저장되었으나 시스템은 알지 못함 | 전송 오류, 펌웨어 버그 |

---

### 47.2 LSE(숨어있는 섹터 에러)의 대응

- **LSE는 탐지가 쉬움** → RAID와 같은 중복 저장 기술로 복구 가능.
- RAID-5 → 패리티 기반 복구  
- NetApp RAID-DP → 이중 패리티로 LSE와 디스크 고장 동시 대응  
- 디스크 정기 검사를 통해 대부분의 LSE를 사전에 파악 가능

---

### 47.3 손상 검출: 체크섬

- 손상된 블럭은 시스템이 직접 알 수 없기 때문에 **체크섬 기반 검출** 필요
- 체크섬 = 데이터 요약값. 저장 당시와 읽기 당시 값을 비교하여 손상 여부 판단

#### ✅ 대표적인 체크섬 알고리즘

| 이름 | 설명 | 특징 |
|------|------|------|
| XOR | 열 단위로 XOR | 단순하지만 충돌 가능 |
| 덧셈 | 2의 보수 합 | 빠르지만 shift에 취약 |
| Fletcher | s1, s2 합산 | CRC 수준의 강력함 |
| CRC | 나머지 연산 | 강력한 검출력, 네트워크 등에서 많이 사용 |

---

### 47.4 체크섬의 배치와 사용 방식

- **배치 위치**:
  - 섹터에 같이 저장 (예: 520B 섹터 중 8B를 체크섬으로 사용)
  - 별도 섹터에 체크섬만 저장 → 쓰기 시 I/O 오버헤드 증가
- **사용 흐름**:
  1. 블럭 `D` 읽음
  2. 저장된 체크섬(Cs(D)) 획득
  3. 블럭으로부터 계산된 체크섬(Cc(D)) 획득
  4. Cs == Cc 여부로 손상 판단

---

### 47.5 잘못된 위치에 기록 (Misdirected Write)

- 시스템은 쓰기를 올바르게 수행했다고 판단하지만, **주소가 틀린 곳에 기록**되는 문제
- 해결 방법: **체크섬에 블럭의 식별 정보(디스크 번호, 오프셋 등)** 포함 → 기록 위치 검증 가능

---

### 47.6 기록 작업의 손실 (Lost Write)

- 디스크가 쓰기 성공을 알렸지만 실제론 저장되지 않은 오류
- 기존의 체크섬 + 물리 ID 기법으론 탐지 불가능

#### 대응 방법

| 방법 | 설명 |
|------|------|
| Read-after-write | 쓰기 후 즉시 다시 읽어 확인 |
| ZFS 방식 | 체크섬을 **데이터 외부(아이노드 등)에 저장**하여 불일치 탐지 |

---

### 47.7 Scrubbing

- 데이터에 **접근이 거의 없는 경우** 오류를 감지할 수 없으므로, **정기적 전체 검사 필요**
- Scrubbing은 백그라운드에서 **모든 블럭을 주기적으로 읽고 체크섬 비교**

---

### 47.8 체크섬의 오버헤드

- **공간**:
  - 4KB 당 8바이트 체크섬 → 약 0.19% 디스크 공간 차지
- **시간**:
  - 쓰기 시 체크섬 연산 → CPU 비용
  - 읽기 시 다시 계산 후 비교 → 추가 비용
- **I/O 증가**: 별도 체크섬 저장 시 I/O 2배 가능

---

## ✅ 요약 정리

| 문제 | 설명 | 해결 방법 |
|------|------|------------|
| LSE | 섹터 손상 | RAID, 이중 패리티 |
| 블럭 손상 | 조용한 오류 | 체크섬 비교 |
| 잘못된 위치 기록 | 주소 오기록 | 블럭 ID 포함 체크섬 |
| 기록 손실 | 쓰기 누락 | read-after-write, 외부 체크섬 |
| 노출 안된 오류 | 접근 없는 블럭 | scrubbing |

- **체크섬**은 무결성을 보장하는 강력한 도구이지만 완벽하진 않다.
- 시스템은 오류의 종류에 따라 **여러 기술을 조합해 사용**해야 하며,  
  이를 통해 높은 신뢰성의 저장 시스템을 구축할 수 있다.
