# 📦 로그 기반 파일 시스템 (OSTEP Chapter 46)

Berkeley 대학의 John Ousterhout 교수와 Mendel Rosenblum이 제안한 **로그 기반 파일 시스템(Log-structured File System, LFS)**은 디스크 쓰기 성능을 향상시키기 위해 기존의 파일 시스템 구조를 근본적으로 재설계한 시스템이다.  
LFS는 모든 쓰기 작업을 순차적으로 처리하여 **디스크 대역폭을 최대한 활용**하는 것을 목표로 하며, **쓰기 위주의 워크로드**, **RAID 환경**, 그리고 **메타데이터 갱신**이 많은 현대 파일 시스템에서 효과적이다.

---

## ❓ 핵심 질문

> 어떻게 하면 모든 파일 시스템 쓰기를 **순차적 디스크 쓰기**로 변환할 수 있을까?

---

## 🔍 상세 개념 정리 (Part 1)

### 46.1 디스크에 순차적으로 쓰기

- 모든 파일 시스템 갱신(write)을 **순차적으로 디스크에 기록**하고자 하는 것이 LFS의 핵심 목표
- 기존 FFS는 하나의 작은 파일 생성에도 여러 블록에 여러 번 쓰기를 발생시켜서 비효율적임
- LFS는 이러한 비효율을 줄이기 위해 한 번에 큰 덩어리로 기록하는 전략을 채택

---

### 46.2 갱신 내용 모으기: 세그멘트

- LFS는 **갱신 내용을 세그멘트(segment)**라는 메모리 버퍼에 먼저 모아둠
- 세그멘트는 수십 KB ~ 수 MB 크기로, **버퍼가 가득 찼을 때 한 번에 디스크에 기록**
- 단점: 같은 파일의 블록들이 여러 세그멘트에 흩어져 있을 수 있음 → 읽기 시 비효율

#### ✅ 예시
- 파일 j에 블록 4개 추가 → 세그멘트에 기록
- 파일 k에 블록 1개 추가 → 같은 세그멘트에 기록
- 이 5개의 블록은 함께 디스크에 순차적으로 저장됨

---

### 46.3 적절한 버퍼의 크기는?

- 세그멘트 크기를 결정하는 기준:
  - 디스크 탐색 + 회전 지연 시간(T<sub>seek</sub>)
  - 디스크 전송 속도(R<sub>peak</sub>)
- **목표**: T<sub>seek</sub> 시간 동안 R<sub>peak</sub>만큼의 데이터를 쓰기 위해 충분한 크기를 설정해야 함
- 일반적으로 몇 MB 수준의 세그멘트가 이상적

---

### 46.4 덮어쓰지 않고 새로운 위치에 쓰기

- LFS는 기존 블록을 **덮어쓰지 않음**
- 항상 새로운 위치(빈 공간)에 데이터, 아이노드 등을 연속적으로 기록
- 덕분에 **모든 디스크 쓰기를 순차적 쓰기로 구현 가능**
- 기존 버전의 데이터는 디스크에 그대로 남아 있음

---

### 46.5 간접 계층을 이용한 해법: 아이노드 맵 (imap)

- 문제: 아이노드가 디스크 곳곳에 흩어져 있고, **위치가 계속 변함**
- 해결책: **아이노드 번호 → 디스크 주소**를 매핑하는 **아이노드 맵(imap)** 사용
- imap은 배열 형태이며, 각 항목은 아이노드 번호와 그에 해당하는 디스크 주소를 기록
- 데이터가 갱신되면 imap도 함께 갱신하여 최신 주소를 반영함

---

### 46.6 최종 완성: 체크포인트 영역

- 문제: imap 자체도 계속 변하기 때문에 어디 있는지 알 수 없음
- 해결책: 디스크의 정해진 위치에 **imap의 위치 정보를 기록하는 블록 → 체크포인트 영역(CR)**  
- CR은 디스크의 맨 앞/뒤에 존재하고, **주기적으로 갱신**됨 (예: 30초 주기)
- CR에는 imap 블록들의 위치(주소)가 저장되어 있음

---


### 46.7 디스크에서 읽기: 요약

- **기존 파일 시스템**: inode의 고정 위치를 알고 있으므로 바로 접근 가능
- **LFS**: inode가 계속 새로운 위치에 쓰이므로, `inode map(imap)`을 먼저 찾아야 함
- 읽기 흐름:

```text
1. 체크포인트 영역 → imap 위치 찾기  
2. imap → inode 위치 찾기  
3. inode → 데이터 블록 주소 얻기  
4. 디스크에서 실제 데이터 블록 읽기
```

> 📌 읽기 성능은 쓰기보다는 느릴 수 있음 → 캐시와 순차적 배치를 통한 보완 필요

---

### 46.8 쓰기 동작의 효율성

- LFS는 **쓰기 성능이 매우 우수**함  
  - 모든 데이터를 순차적으로 쓰기 때문
  - 디스크 탐색(seek) + 회전 지연(rotational delay) 거의 없음

- 디스크 대역폭을 거의 최대한 활용할 수 있음

> 단, 읽기 작업은 여전히 성능 저하 가능성이 있음 → 구조적 trade-off

---

### 46.9 가비지 컬렉션의 필요성

- LFS는 **덮어쓰기 대신 append** 방식 → 시간이 지나면 "죽은(old)" 데이터가 많아짐
- 이 데이터를 **수거하고 디스크 공간을 회수**하는 작업이 필요함 → **가비지 컬렉션(GC)**

---

### 46.10 블럭의 최신 여부 판단

- GC 중 어떤 블럭이 "살아있는지" 확인해야 함
- **최신 블록 판단 기준**: imap에 있는 디스크 주소와 일치하는가?

#### 예시

| 블록 주소 | imap 주소와 일치 | 상태 |
|-----------|------------------|------|
| 0xABCD    | ❌ 불일치         | 죽은 블록 |
| 0xBEEF    | ✅ 일치           | 살아있는 블록 |

> 이 과정을 통해 세그먼트 내 "살아있는" 블록만 남기고 나머지는 제거

---

### 46.11 어떤 세그먼트를 언제 정리할 것인가?

- 가비지 컬렉션의 **정책(policy)** 은 중요하다:

| 전략 | 설명 |
|------|------|
| greedy | 살아있는 블록이 가장 적은 세그먼트부터 정리 |
| cost-benefit | 블록 수, 회수 비용, 회수 효율 등을 모두 고려 |
| age-based | 오래된 세그먼트부터 정리 |

- 현실 시스템은 여러 정책을 **혼합**하여 사용함

---

### 46.12 크래시로부터의 복구와 로그

- LFS는 본질적으로 **로그 기반**이기 때문에, 크래시 복구가 매우 간단
- 체크포인트 영역만 읽으면, 시스템은 가장 최신 imap을 바로 찾을 수 있음
- 트랜잭션의 atomicity도 자연스럽게 보장됨 (세그먼트 단위 기록)

> LFS의 큰 장점 중 하나: **쓰기 성능 + 일관성 보장 + 빠른 복구**

---

### 46.13 요약

- LFS는 기존 파일 시스템과 완전히 다른 **쓰기 방식**을 사용
- 모든 쓰기를 **순차적인 append**로 처리하여 성능 향상
- 읽기 성능은 보완이 필요하나, **캐시 전략과 메타데이터 튜닝**으로 보완 가능
- 가비지 컬렉션과 체크포인트 구조는 **복잡하지만 강력한 신뢰성** 제공

---

## ✅ 전체 요약 표

| 항목 | 설명 |
|------|------|
| **순차적 쓰기** | 모든 갱신 데이터를 append-only 방식으로 기록 |
| **세그먼트 구조** | 일정 크기의 단위로 데이터를 모아서 연속 기록 |
| **imap** | inode 번호 ↔ 실제 위치 매핑 테이블 |
| **체크포인트 영역** | 최신 imap 위치를 저장하는 고정 디스크 위치 |
| **읽기 흐름** | checkpoint → imap → inode → data |
| **쓰기 성능** | 디스크 대역폭 최대 활용 (순차 쓰기) |
| **가비지 컬렉션** | 죽은 블록 회수 → 공간 재활용 |
| **최신성 판단** | imap 주소와 비교하여 결정 |
| **GC 정책** | greedy, cost-benefit, age-based 혼합 사용 |
| **복구** | checkpoint 기반 → 빠르고 안전한 복구 가능 |
