# 🔒 데드락(Deadlock) 기초 정리

> 여러 스레드(또는 프로세스)가 **서로가 가진 자원을 기다리며 영원히 대기**하는 상태를 데드락이라 한다.  
> 게임 서버/네트워크 라이브러리 같이 **멀티스레드**가 기본인 환경에서 필수로 이해해야 하는 주제.

---

## ❓ 무엇이 원인인가? — Coffman의 4가지 필요 조건

데드락은 아래 **네 가지 조건이 모두** 만족될 때만 발생한다. 하나라도 깨면 데드락은 **원천 차단**된다.

1. **상호 배제(Mutual Exclusion)**  
   - 자원(뮤텍스, 파일, 소켓 등)은 한 시점에 **오직 한 스레드만** 사용 가능.
2. **점유 대기(Hold and Wait)**  
   - 어떤 스레드가 **자원을 보유한 채**로 **다른 자원**을 추가로 기다림.
3. **비선점(No Preemption)**  
   - 이미 점유한 자원을 **강제로 빼앗을 수 없음**. 자발적 해제만 가능.
4. **순환 대기(Circular Wait)**  
   - 스레드 A는 자원 X를 들고 자원 Y를 기다리고, 스레드 B는 자원 Y를 들고 자원 X를 기다리는 식의 **원형 대기 고리**가 존재.

> 실무 감각: 상호 배제는 대부분 필요하므로 없애기 어렵고, **점유 대기**·**순환 대기**를 끊는 전략이 주로 쓰인다.

## 🧪 최소 예제로 보는 데드락

### 예제 1: **락 순서 역전(Lock Order Inversion)**

```cpp
#include <mutex>
#include <thread>
#include <iostream>

std::mutex m1, m2;

void worker1() {
    std::lock_guard<std::mutex> lk1(m1);      // m1 먼저
    std::this_thread::sleep_for(std::chrono::milliseconds(10));
    std::lock_guard<std::mutex> lk2(m2);      // 그다음 m2
    std::cout << "worker1 done\n";
}

void worker2() {
    std::lock_guard<std::mutex> lk2(m2);      // m2 먼저
    std::this_thread::sleep_for(std::chrono::milliseconds(10));
    std::lock_guard<std::mutex> lk1(m1);      // 그다음 m1
    std::cout << "worker2 done\n";
}

int main() {
    std::thread t1(worker1), t2(worker2);
    t1.join(); t2.join();
}
```

- `worker1`은 **m1 → m2**, `worker2`는 **m2 → m1** 순서로 획득.  
- 타이밍이 맞으면 **서로 상대 락을 기다리며** 영원히 대기 ⇒ 데드락.

#### 해결 1) **락 순서 통일**
- 모든 코드에서 **항상 m1 → m2 순서**로만 잠금.
- 규칙 하나로 **순환 대기** 조건을 깬다.

```cpp
void worker1() {
    std::scoped_lock lock(m1, m2); // C++17, 교착 회피 알고리즘 내장
    std::cout << "worker1 done\n";
}
void worker2() {
    std::scoped_lock lock(m1, m2); // 항상 같은 순서로 획득되도록 보장
    std::cout << "worker2 done\n";
}
```

> 팁: C++11에서는 `std::lock(m1, m2); std::lock_guard<std::mutex> lk1(m1, std::adopt_lock); ...` 패턴도 사용.

## 🧩 실무에서 자주 터지는 패턴들

1. **중첩 락 + 순서 불일치**  
   - 모듈 A는 (m1→m2), 모듈 B는 (m2→m1)로 잠그는 경우.  
   - **모듈 경계를 넘는 규칙 합의**가 중요.

2. **락 보유 상태에서 블로킹 I/O/대기**  
   - 뮤텍스를 쥔 채로 `recv()`, 디스크 I/O, `join()`/`wait()` 등을 호출.  
   - 임계 구역은 **짧게** 유지하고, **락 밖에서** 느린 작업을 수행.

3. **콜백을 락을 잡은 채로 호출**  
   - 호출된 콜백이 **다시 같은 락**을 잡으려 하면 **자기 교착(Self-deadlock)** 발생.  
   - 해결: 콜백 호출 전 **락 해제** or **락을 잡지 않는 설계**.

4. **재귀적 잠금 필요성 오판**  
   - 같은 스레드가 **동일 뮤텍스**를 두 번 잠그면 데드락.  
   - 정말 필요할 때만 `std::recursive_mutex` 고려(가능하면 설계로 회피).

5. **락 + 조건 변수 사용 실수**  
   - `notify_one()`를 락을 오래 쥔 채로 호출하면, 깨어난 스레드는 다시 락을 얻지 못해 **머무를 수 있음**.  
   - 일반적으로 **상태 갱신 → notify → (락 해제)** 순서를 지키고, 대기 측에서는 **while-조건**으로 검사.

## 🛡️ 예방/회피 전략 체크리스트

- **락 순서 규약** 수립  
  - “항상 m1 → m2 → … 순서로 잠근다.”  
  - 공동체 규칙 + 코드 리뷰에서 강제.

- **여러 락은 한 번에 획득**  
  - `std::scoped_lock(m1, m2, m3)` 또는 `std::lock` + `adopt_lock`.

- **임계 구역 최소화**  
  - 락 안에서는 **상태 갱신만**. I/O, 동적 할당, 긴 연산, 외부 콜백은 락 밖에서.

- **try_lock / timed_mutex로 회피**  
  - 응답성이 중요할 때: 실패하면 **백오프/재시도** 또는 **우회 경로**.

  ```cpp
  std::timed_mutex m;
  if (m.try_lock_for(std::chrono::milliseconds(1))) {
      // 작업
      m.unlock();
  } else {
      // 우회 처리 or 재시도
  }
  ```

- **락 계층/레벨 도입**  
  - 각 락에 **우선순위(계층)**를 부여, 낮은 번호 → 높은 번호 순서로만 획득.

- **데드락 안전 유틸 사용**  
  - C++17 `std::scoped_lock`, C++11 `std::lock` 패턴 적극 활용.

## 🧭 데드락 vs 라이브락 vs 기아(Starvation)

- **데드락**: 참여 스레드 모두 **진행 불가**(정지).  
- **라이브락**: 모두 동작하긴 하는데 **진행이 없음**(계속 서로 양보만).  
- **기아**: 한 스레드가 **계속 스케줄링/자원 획득에서 밀려** 진행 못함.

> 원인과 해결책이 다르므로 **증상 구분**이 중요하다.

---

## 🛠️ 디버깅 힌트

- **락 순서 로깅**: 잠금 직전/해제 직후 로그, 스레드 ID와 함께.  
- **스레드/락 덤프**: 플랫폼 도구(Visual Studio Concurrency Visualizer, clang/gcc ThreadSanitizer 등)로 대기 관계 확인.  
- **리소스 할당 그래프**: “스레드 ↔ 자원” 그래프에 **사이클**이 있으면 데드락.

---

## ✅ 요약

- 데드락은 **상호 배제, 점유 대기, 비선점, 순환 대기** 4조건이 모두 성립할 때 발생.  
- 가장 흔한 원인은 **락 순서 역전**.  
- **락 순서 통일**, **여러 락 동시 획득(`std::scoped_lock`)**, **임계 구역 최소화**, **콜백 호출 시 락 해제**가 실전 핵심.  
- 증상(데드락/라이브락/기아)을 구분하고, 도구와 로깅으로 **대기 그래프**를 추적하자.
